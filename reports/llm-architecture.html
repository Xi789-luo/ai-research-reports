大模型技术架构全景

一家大模型公司真正的技术能力，不在某一层最强，而在六层之间能否低损耗地循环：算力变成有效算力，数据变成配方，训练变成能力，推理变成收入，反馈再变成下一轮数据。

结论先行

  1. 大模型技术架构不是六层堆叠，而是三条闭环：训练闭环、推理闭环、数据闭环。 算力、训练基础设施、数据、模型、推理、产研工程只是节点；真正的能力差在回路速度与接口损耗。一条训练流水线每多等一天数据、每多一次 checkpoint 不兼容、每多一轮评测污染，都会把算力优势抵消掉。需要强调的是：不同阶段的瓶颈不同，0→1 的瓶颈通常是模型与数据，1→10 的瓶颈通常是训练稳定性，10→100 的瓶颈通常是推理成本与组织接口。
  2. 算力层的核心不是「有多少卡」，而是「有多少有效算力」。 有效算力 ≈ 峰值算力 × 利用率 × 互联效率 × 稳定性 × 调度效率。行业训练 MFU 常在 35%–45%，字节 MegaScale 在 12,288 卡上做到 55.2%，已经是头部水平；同样的卡，利用率差两倍，产出就差两倍。需要强调的是：MFU 的计算口径（模型 FLOPs、序列长度、是否含重算）不同，不能直接横比。
  3. 训练基础设施的核心是「并行组合 + 故障恢复」，不是「选一个框架」。 千卡看并行（DP/TP/PP/EP/CP 怎么切），万卡看网络与容错（NCCL、RDMA、checkpoint、straggler），十万卡看电力、调度与集群运营。框架会趋同，调优经验与故障库不会。需要强调的是：公开的 MFU 数字往往来自理想 workload，真实训练的长时间稳定性才是分水岭。
  4. 数据基建是供应链，数据算法是配方；两者常被混为一谈。 基建管吞吐、成本、lineage、合规；算法管配比、合成、课程、污染、飞轮。把「爬了 10T token」当成数据能力，就像把「买了面粉」当成会做面包。需要强调的是：数据量不等于数据质量，合成数据也不等于免费数据——合成需要验证器、过滤与去重，成本常常被低估。
  5. 推理部署是唯一直接决定毛利率的层。 训练是资本开支，推理是运营成本；$/1M tokens、p99、goodput、KV cache 命中率、GPU 利用率，决定商业模式能不能成立。推理优化必须与模型结构、训练精度、checkpoint 格式联合设计，事后补课的成本很高。需要强调的是：低价 API 不等于低成本，可能只是用融资补贴推理。
  6. 产研工程是把「研究能力」变成「可重复交付」的层，也是最容易被低估的层。 实验管理、CI/CD、eval harness、release gate、安全、客户交付，决定了模型能否从 demo 变成产品。没有这一层，研究团队会陷入「每次都要重新跑一遍」的泥潭。需要强调的是：产研工程不是支持部门，它是规模化后的主战场。
  7. 组织架构没有唯一答案，但有一条规律：越靠近前沿，越需要「研究—infra—数据」共置；越靠近规模，越需要平台化与接口契约。 七家公司的差异，本质是「共置」与「平台化」的比例不同：DeepSeek 用极小的共置团队做模型-基础设施协同设计，字节用平台（MegaScale/veScale/Volcano）+ 1,500 人 Seed 做规模化，Anthropic 用研究/产品/政策的清晰分工做安全与产品。需要强调的是：照搬别家的 org chart 会失败，因为阶段、瓶颈与人才结构不同。

01.2四个接口：层与层之间真正需要「签约」的地方

架构损耗大多发生在接口，而不是层内。四个接口必须有明确的 owner、版本与验收标准。
接口生产方消费方必须写清什么典型失败
Checkpoint 契约 训练基础设施 推理部署、后训练 张量布局、并行切分、精度、tokenizer、config、版本兼容 训练完的 checkpoint 推理引擎加载不了；量化后精度崩；并行度改变后无法续训

评测契约 模型团队 / 评测团队 产研工程、产品、发布委员会 benchmark 版本、prompt、采样参数、人类基线、污染声明、通过阈值 榜单涨了但真实体验没涨；eval 泄漏；不同团队用不同口径汇报

一条公式

有效算力 ≈ 峰值算力 × 利用率 × 互联效率 × 稳定性 × 调度效率。采购只能改变第一项；后四项由架构、运维与组织决定。这也是为什么「买更多卡」经常不是瓶颈的答案。

02

算力层：把电力、芯片、网络、存储、调度、运维、运营组合成一台机器

算力层最容易被简化成「买了多少张卡」。但在真实集群里，卡只占 TCO 的一部分；网络、存储、电力、运维与利用率，才决定这些卡能不能持续产出 token。

02.1九个模块：算力层的完整拆分

C1 · 硬件
服务器与加速卡

GPU/NPU/TPU、HBM 容量与带宽、卡间互联、整机形态、采购/租赁/云。决定峰值算力与显存上限，也决定可用的精度（FP8/FP4）。

C2 · 互联
节点内与集群网络

NVLink/PCIe、InfiniBand/RoCE、超节点、叶脊拓扑、拥塞控制。决定张量并行、专家并行与流水并行的可扩展性。

C3 · 存储
并行文件系统与对象存储

训练数据、checkpoint、日志、模型权重。要求高吞吐、低延迟、POSIX 兼容、PB 级扩展；DeepSeek 3FS 是公开样本。

C4 · 调度
集群调度与多租户

Slurm/Kubernetes/Volcano、队列、配额、抢占、拓扑感知、gang scheduling。决定集群是「一台机器」还是「一堆孤岛」。

C5 · 运维
SRE、容灾与备件

监控、告警、故障隔离、备件、固件/驱动升级、灰度、混沌演练。万卡集群的可用性，靠的是运维体系而不是运气。

C6 · 机房
电力、制冷与选址

MW 级供电、PUE、液冷、土地、电价、网络时延。十万卡时代的真正瓶颈往往不是芯片，而是电力和并网。

C7 · 异构
国产卡与软件栈适配

CUDA/ROCm/CANN、算子库、编译器、通信库、框架适配。差距常在显存带宽与生态，不只是峰值算力。

C8 · 运营
FinOps 与算力经营

成本归因、利用率、预留/竞价、预算、内部计价、集群共享。没有成本可见性，就没有优化动力。

C9 · 观测
集群可观测性

GPU 利用率、显存、温度、功耗、NCCL 状态、网络丢包、存储 IOPS。故障定位的第一现场。

02.3千卡、万卡、十万卡：瓶颈会换位置

集群规模每上一个量级，瓶颈就从「并行策略」转向「网络/存储/电力/组织」。用千卡经验管万卡，通常会低估运维与调度。
规模主要瓶颈必须有的能力组织含义
千卡并行策略、显存、MFUMegatron/DeepSpeed/FSDP、NCCL 调优、checkpoint一个训练平台小组 + 模型团队共置
万卡网络、存储、故障率、调度拓扑感知、RDMA、并行文件系统、自动容错、SRE独立集群团队；训练/推理分池；容量规划
十万卡电力、并网、集群运营、跨域调度MW 级供电、液冷、超节点、全局调度、FinOps基础设施成为公司级能力；CEO/CTO 直接负责

公开样本：字节 MegaScale 在 12,288 张 GPU 上做到 55.2% MFU，说明万卡集群的瓶颈不只是卡，而是网络、调度与故障恢复的系统工程；DeepSeek 的 3FS 在 180 节点集群上公开了约 6.6 TiB/s 的读吞吐，说明存储可能成为训练吞吐的隐形上限；阿里灵骏、腾讯 Angel 等平台则把「集群—框架—模型」做成了一体化栈。需要强调的是：这些数字来自各自公开材料，测试条件不同，不能直接横比。

算力层最常见的三个误判

① 把峰值算力当有效算力。峰值是理论值，MFU 才是产出。② 把云当无限弹性。大集群的瓶颈是配额、网络与电力，不是 API。③ 把推理卡和训练卡混在一起。训练要互联与显存，推理要吞吐与成本，混池会同时拖累两边。

03

训练基础设施：把「能训」变成「稳定地训完」

训练基础设施的目标不是「把模型跑起来」，而是「在尽可能长的时间里，以尽可能高的 MFU，稳定地训完，并且随时能恢复」。这是一项系统工程，不是选一个框架。

03.1八个模块

T1 · 框架
训练框架

PyTorch/JAX、Megatron-LM、DeepSpeed、FSDP、veScale 等。负责计算图、自动微分、分布式抽象与算子调度。

T2 · 并行
并行策略

数据并行（DP）、张量并行（TP）、流水并行（PP）、专家并行（EP）、序列/上下文并行（CP）。决定模型能切多大、通信有多少。

T3 · 显存
显存与计算优化

ZeRO、激活重算、offload、融合算子、梯度累积。目标是在有限 HBM 下装下更大的模型与更长的序列。

T4 · MoE
MoE 训练

路由、负载均衡、capacity factor、dropless、专家并行、EPLB。MoE 的难点不是参数，而是「不均衡」。

T5 · 精度
混合精度与数值稳定

BF16/FP8/FP4、loss scaling、梯度裁剪、QK-clip、随机数复现。精度是吞吐的来源，也是 NaN 的来源。

T6 · 容错
Checkpoint 与故障恢复

分片 checkpoint、异步保存、断点续训、弹性训练、straggler 检测。万卡集群里，故障是常态，不是异常。

T7 · Kernel
算子与编译器

FlashAttention、DeepGEMM、Triton/CUDA kernel、图编译、通信融合。决定同样的卡能多跑出多少 tokens。

T8 · 观测
实验管理与可观测

loss/grad norm、MFU、tokens/s、显存、通信耗时、config/seed/数据版本。没有可复现，就没有研究。

训练基础设施的分工边界

模型团队决定模型结构、并行约束与训练目标；训练平台团队负责框架、并行、checkpoint、容错与性能；SRE/集群团队负责硬件、网络、存储与故障；数据团队负责数据供给与版本。四者的接口是 checkpoint、数据契约与训练配置。边界不清时，最常见的结果是「模型团队在调框架，平台团队在猜模型」。

04

推理部署：唯一直接决定毛利率的层

训练是资本开支，推理是运营成本。一个模型能不能赚钱，最终落在 $/1M tokens、p99、goodput 和 GPU 利用率这四个数字上。

04.1九个模块

I1 · 网关
API Gateway

鉴权、限流、配额、路由、计费、内容安全。它是产品与模型之间的第一道契约。

I2 · 调度
请求调度

continuous batching、优先级、抢占、多租户隔离、SLA 分级。决定吞吐与尾延迟。

I3 · 引擎
推理引擎

vLLM、SGLang、TensorRT-LLM、自研引擎。负责图执行、批处理、内存管理与并行。

I4 · KV
KV Cache 管理

PagedAttention、prefix caching、KV 量化/offload、跨请求复用。长上下文时代的核心内存问题。

I5 · 量化
量化与压缩

FP8/INT8/INT4、AWQ/GPTQ、平滑量化、精度评估。用精度换吞吐与显存，但要守住任务指标。

I6 · 投机
投机解码

草稿模型、Medusa/EAGLE、n-gram/检索草稿。接受率高时提速，接受率低时反而更慢。

I7 · PD
Prefill/Decode 分离

把长 prompt 的 prefill 与自回归 decode 拆到不同资源池，按负载独立扩缩容。

I8 · 多租户
多模型/多 LoRA

基础模型 + LoRA/adapters、路由、隔离、配额。企业客户需要私有化与专属实例。

I9 · 观测
SLO 与成本

TTFT、TPOT、p99、goodput、缓存命中、每 token 成本、GPU 利用率、错误率。

04.3训练-推理协同：五个必须在训练前想清楚的问题

  1. Checkpoint 格式：推理引擎能不能直接加载？并行切分是否可重排？量化后是否保留关键层精度？
  2. Attention/ KV 布局：GQA/MLA/MQA 的选择，直接决定 KV cache 大小与推理吞吐；训练时就要为推理留好结构。
  3. Tokenizer 与上下文：tokenizer 变更会让缓存、计费、评测全部失效；长上下文能力要与推理显存规划一起定。
  4. 精度策略：训练用 FP8、推理用 FP8/INT4，精度回退要在训练时用 QAT 或校准数据评估，不能上线后再补。
  5. SLO 与模型结构：如果产品要求 p99 < 2s，模型层数、专家数、激活参数、上下文长度都要为推理成本让路。
推理成本公式

$/1M tokens ≈ (GPU 每小时成本 ÷ 每小时有效 token 数) × 1,000,000 + 网络/存储/运维分摊。降低分子（采购、租赁、利用率）和抬高分母（吞吐、缓存、批处理）同样重要。很多团队只优化模型，不优化利用率，结果卡买了、成本没降。

公开样本：DeepSeek 公开过推理系统的成本与利润率口径，说明推理层的成本可以被工程显著改变；字节 MegaScale-Infer 研究了 MoE 的 disaggregated expert parallelism；vLLM/SGLang 把 PagedAttention、continuous batching、prefix caching 变成行业基线；腾讯 TurboTransformers 则展示了推理引擎与业务场景联合优化的路径。需要强调的是：这些系统的测试条件、模型与负载不同，不能直接比较绝对数字。

05

数据基建：LLM 的供应链，不是「数据湖」

数据基建的目标不是「把数据存下来」，而是「以可控成本、可追溯、可复现的方式，把原始数据变成可训练的 token」。它是一条供应链，不是一个存储桶。

05.1十五个模块：从原始数据到训练 token

D1 · 来源
数据源与采集

网页、代码、书籍、论文、对话、业务日志、合成数据、标注数据。每一类都有许可、隐私、质量与成本约束。

D2 · 存储

D4 · 计算

Spark、Ray、Flink、DuckDB、Beam。批处理、流处理、分布式推理、向量化。

D5 · 解析
解析与清洗

HTML→text、PDF/表格/公式解析、语言识别、去噪、结构还原。解析质量常被低估。

D6 · 去重
去重

MinHash/SimHash、精确哈希、embedding 聚类、文档级/段落级。直接影响 token 效率与记忆。

D7 · 质量
质量与安全

规则、分类器、LLM judge、PII、毒性、版权、许可。需要黄金集与人工抽检。

D8 · 配方
配比与课程

D9 · 合成
合成数据

self-instruct、演化、self-play、任务生成、验证器。合成不是免费数据，需要过滤与评估。

D10 · Tokenize

D11 · 版本
版本与 Lineage

数据集版本、内容哈希、父数据集、处理代码、配置。回答「这个 run 到底用了什么」。

D12 · 评测
评测数据与污染

held-out、动态 eval、n-gram/embedding 污染检测、去污染、评测集版本。防止「考卷泄题」。

D13 · 标注
标注与人类反馈

标注体系、众包/专家、一致性、偏好数据、红队数据。决定后训练的上限。

D14 · 成本
成本与可观测

每 1T token 的存储/计算/人工成本、吞吐、失败率、重跑率。数据成本常被低估。

D15 · 契约
数据契约与 SLA

schema、版本、owner、交付时间、质量阈值、回滚策略。让数据团队与训练团队有可执行的接口，而不是口头承诺。

K1
质量

K2

太简单学不到，太难学不动。课程与难度分层要与模型规模、训练阶段匹配。

产品日志、新事件、新代码。新鲜数据提升时效性，但带来隐私、噪声与污染风险。

07.1架构选择如何反向决定基础设施

模型架构不是「研究团队自己的事」。每一个结构选择都会在训练与推理层产生账单：

  • MoE：参数量可以做大，但带来专家并行、负载均衡、all-to-all 通信与 EPLB。MoE 的推理还需要专家并行/分层部署，否则单卡放不下。
  • MLA/GQA：压缩 KV cache，直接降低长上下文推理的显存与带宽；但训练时的 attention kernel 更复杂，推理引擎需要专门支持。
  • 长上下文：训练需要序列/上下文并行、激活重算、长序列数据；推理需要 chunked prefill、KV 分页/offload、PD 分离。
  • 多模态：数据量、存储、预处理、视觉编码器与对齐训练都会膨胀；推理侧还要处理图像/视频的预处理与带宽。
  • 推理模型（长思维链）：训练需要大规模 rollout 与验证器；推理成本随思考长度线性上升，必须用缓存、批处理与预算控制。
一个常见的组织错位

模型团队选了一个「训练指标最好」的结构，推理团队上线时才发现 KV cache 放不下、专家并行通信太贵、量化精度崩。正确的做法是：架构评审必须有推理与训练 infra 的人在场，并把「每 token 成本」作为架构决策的一等指标，而不是上线后再优化。

产研工程：把研究能力变成可重复交付

研究团队可以靠个人能力做出一次 demo；产品团队必须靠工程体系每天交付。产研工程就是这两者之间的桥：实验可复现、发布可回滚、评测可比较、事故可定位。

08.1十个模块

E1 · 实验
实验管理与模型注册

config、seed、数据版本、代码 commit、指标、checkpoint。回答「这个结果是怎么来的」。

E2 · CI/CD
训练/评测流水线

代码检查、单测、数据校验、训练启动、评测、产物归档。把「手动跑」变成「可重放」。

E3 · Eval
评测 harness

benchmark、prompt 模板、采样参数、人类基线、回归集、污染检测。评测口径必须统一。

E4 · Gate
发布门禁

能力、回归、安全、成本、延迟五类 gate；不达标不发布，或降级发布。

E5 · 安全
安全与红队

越狱、注入、数据泄漏、有害内容、模型窃取；上线前红队，上线后监控。

E6 · 观测
线上可观测

请求、延迟、错误、token、成本、用户反馈、模型版本；按版本/租户/场景切片。

E7 · API
API/计费/多租户

鉴权、限流、配额、计费、路由、灰度、版本兼容。API 是模型公司的产品契约。

E8 · 交付
企业交付/FDE

VPC/私有化、数据隔离、SLA、定制评测、现场调试。企业收入靠交付，不靠 API 文档。

E9 · 文档
开发者体验

API 文档、SDK、示例、错误码、迁移指南。降低集成成本，就是降低获客成本。

E10 · 复盘
事故与复盘

事故分级、止损、根因、行动项、回归测试。把一次事故变成一条防线。

08.2四个 gate：数据、训练、评测、发布

每个 gate 都要有明确的 owner、通过标准与回滚方案。没有 gate 的流水线，只是「更快地发布问题」。

08.3研究到产品的死亡谷：五个断点

  1. 不可复现：研究结果依赖某个人的本地环境、随机种子、未提交的数据。产品团队无法接手。
  2. 评测不一致：研究用一套 prompt，产品用另一套；榜单涨了，用户体验没涨。
  3. 成本失控：研究追求效果，不考虑 tokens/s 与 $/1M tokens；上线后毛利为负。
  4. 安全缺口：研究只测能力，不测越狱/注入/数据泄漏；上线后被红队打穿。
  5. 交付断层：API 能跑，但企业客户要 VPC/私有化/SLA；没有 FDE 与交付团队，收入落不了地。
产研工程的定位

它不是「支持部门」，而是规模化阶段的主战场。当模型能力趋同，谁能更快、更稳、更便宜地把能力交付给客户，谁就赢。产研工程的产出不是「流程」，而是发布频率、事故率、交付周期、单位成本这四个数字。

09.3五个最常见的协同失败

F1GPU 在等数据高

训练集群已经就绪，数据管道还在洗数据；或者数据版本临时变更，训练任务被迫重启。根因：数据与训练没有共享的排期与版本冻结机制。修复：数据 gate + 版本冻结 + 预取/缓存。

F2Checkpoint 不兼容中高

训练团队换了并行度/精度，推理引擎加载不了；或者量化后精度崩。根因：Checkpoint 契约没有 owner。修复：格式版本、加载测试、量化评估纳入训练 gate。

F3评测污染高

训练集混入 eval；榜单涨了，真实能力没涨。根因：数据与评测没有隔离，污染检测不是发布 gate。修复：动态 held-out、污染检测、评测集版本化。

F4上线后 p99 崩中高

离线评测很好，线上长上下文/高并发把 p99 打穿。根因：评测没有覆盖真实负载；推理容量规划缺失。修复：压测、容量规划、灰度、限流、降级。

F5发布没有回滚中高

新模型上线后行为变化，客户投诉，但没有旧版本可回。根因：模型注册/版本管理缺失。修复：模型 registry、灰度、双版本并行、回滚演练。

09.4协作机制：四个固定动作

  • 每周 pipeline review：训练、推理、数据三条流水线一起看，只看瓶颈与接口，不开成汇报会。
  • 模型-基础设施 co-design：新架构评审必须有训练 infra 与推理平台在场，把每 token 成本作为一等指标。
  • 数据-模型 co-design：数据配方变更必须配下游 eval；数据团队参与模型复盘，模型团队参与数据评审。
  • 事故复盘：只问系统与接口，不问「谁背锅」；行动项必须有 owner 与截止日期。

P2

数据

组织设计的一条硬规则

每一个跨团队接口，都必须有一个 owner、一个版本、一个验收标准。没有这三样，平台与研究就会陷入「互相等、互相怪」。接口不是文档，是合同：checkpoint 能不能加载、数据能不能复现、评测口径是否一致、API 是否兼容。

13.1八个结构性风险

R1算力与电力供给极高

高端 GPU 供给、出口管制、MW 级电力与并网，决定训练节奏。算力规划必须以「拿不到最新卡」为前提，不能把希望寄托在采购上。

R2网络与存储成为隐形上限高

万卡训练的瓶颈常从计算转向网络与存储；NCCL hang、checkpoint 写入、数据加载都可能让 GPU 空转。需要拓扑感知、并行文件系统与故障隔离。

R3训练稳定性高

loss spike、NaN、通信故障、数据异常，任何一项都可能让数周训练归零。稳定性不是「调参」，是监控、止损、checkpoint 与复盘的体系。

R4数据质量与污染高

数据错、eval 污染、合成数据自嗨，会让「榜单上涨」变成「能力不涨」。数据 gate 与污染检测必须是发布流程的一部分。

R5推理成本失控高

低价 API、长上下文、长思维链、低利用率，都会让毛利为负。推理成本要按模型/客户/场景核算，不能只看平均。

R6安全与合规中高

越狱、注入、数据泄漏、版权、PII、出口管制；企业客户还会要求私有化与审计。安全不是上线前的红队，是贯穿数据/训练/推理的流程。

R7组织接口债中高

平台与研究互相等、数据与训练排期错位、推理与模型结构不匹配。接口债不会自己消失，只会在关键时刻爆炸。

R8供应商锁定中

云、芯片、推理引擎、数据平台都可能锁定。关键是保留可迁移性：checkpoint 格式、算子抽象、数据格式、API 兼容。

13.2架构自检清单：十个问题

  1. 我们能不能在 30 分钟内说清上一轮训练的 MFU、tokens/s 与故障时间？
  2. 任何一个训练 run，能不能还原它的数据版本、代码 commit、config 与 seed？
  3. Checkpoint 从训练到推理，是否需要人工转换？转换脚本有测试吗？
  4. 训练集与 eval 的污染检测，是发布 gate 还是「有空再跑」？
  5. 推理的 p99 与 $/1M tokens，是否按模型/客户/场景拆分？
  6. 数据管道的每 1T token 成本，是否有人负责？
  7. 模型结构变更时，训练 infra 与推理平台是否在评审现场？
  8. 发布新模型时，能不能在 10 分钟内回滚到旧版本？
  9. 安全红队发现的问题，是否有回归测试与发布门禁？
  10. 如果明天换一家云/一款芯片，哪些层需要重写？

HRBP 与招聘：如何有效支持 AI Infra 团队和业务

AI Infra 是典型「供给窄、岗位定义模糊、价值滞后显现」的组织。HR 如果按普通研发岗招人，通常会在三个地方失效：招错人、配错比、留不住人。HRBP 的价值不是「帮团队招人」，而是把业务路线翻译成人才与组织方案。

14.1先定义：六类岗位，三种人

H1 · 算力
算力平台 / 集群

硬件、网络、存储、调度、SRE。证据是集群规模、MFU、故障恢复时间，不是「用过什么云」。

H2 · 训练
训练基础设施

框架、并行、MoE、checkpoint、kernel。证据是训练稳定性、吞吐与端到端加速。

H3 · 推理
推理平台

引擎、KV cache、量化、PD 分离、SLO。证据是 p99、$/1M tokens 与上线后的保持情况。

H4 · 数据
数据基建

湖仓、管道、去重、质量、lineage。证据是 PB/token 规模、成本与下游 eval 影响。

H5 · 性能
性能 / 内核

CUDA/Triton、编译器、通信库。证据是 kernel 加速比、roofline 分析与端到端收益。

H6 · 运营
容量 / FinOps / 安全

容量规划、成本归因、权限与合规。证据是利用率、单位成本与审计通过率。

② 你做过的最大的端到端性能提升是多少？基线、测试条件、上线后是否保持？
③ 离开大厂平台后，你自己从零搭过什么？
三个问题分别验证：规模、结果、独立性。答不上第三个的人，可能只是「平台使用者」。

Offer：为证据付钱，不为品牌付钱

  • 定价锚点：集群规模、性能结果、故障经验、端到端 ownership；不是「来自哪家大厂」。
  • 结构：现金 + 期权 + 签字费/挖角补偿 + 算力/技术资源；签字费解决未归属股权与空窗，不破坏带宽。
  • 非现金杠杆：集群/卡配额、title、汇报线、远程、开源/会议支持；对 Infra 人往往比多 5% 现金有效。
  • 速度：Infra 候选人通常同时跑 2–4 个流程；电话筛到 offer 控制在 21 天，offer 当天发。
  • 反 counteroffer：先问「除了钱，什么变了」；如果只是加钱，他大概率还会走。

14.5保留：给问题、给资源、给可见度

R1
更大的问题

从单集群到多集群、从训练到推理、从国内到海外；Infra 人的成长来自系统规模，不是职级。

R2
算力与技术资源

明确的卡配额、实验环境、开源/会议支持。对 Infra 人，这比福利更实在。

R3
IC 路径

P5–P8 的技术阶梯，与 manager 路径并行；不要逼所有人转管理。

R4
薪酬 refresh

晋升/关键贡献时追加期权；不要只在新 offer 时给股权。

R5
On-call 公平

轮换、补偿、调休、事故复盘；值班负担要可见、可分配。

R6
可见度

Infra 是成本中心，容易被忽视；公开 credit、技术分享、开源署名，都是保留手段。

早期信号：开始拒绝 on-call；事故里变得沉默；反复说「我们只是成本中心」；拿云厂商/芯片公司/量化的薪酬对比；不再主动提优化想法；代码 review 变少。出现两个以上，HRBP 应主动做 stay interview，而不是等离职。

① 过去一个月，哪件事让你最有成就感？哪件事最消耗你？
② 如果明天离开，最可能的原因是什么？
③ 你希望未来 12 个月掌握什么系统/规模？现在有什么阻碍？
④ 你的 on-call 负担可持续吗？需要怎么调整？
⑤ 如果我只能帮你解决一件事，你希望是什么？ Infra 版 stay interview，每 6 个月一次；由直属上级做，HRBP 记录并跟进

14.7六个常见误区

  • 把 Infra 当纯成本中心。只压价、不投入，最后用更高的故障与流失成本买单。
  • 用算法岗的 JD/面试招 Infra。考刷题与论文，考不出集群、故障与性能。
  • 只看大厂品牌。大厂平台使用者 ≠ 能从零搭系统的人；要问「离开平台后做过什么」。
  • 为速度降 bar。Infra 的坏 hire 会被 on-call 和事故放大，代价高于空缺。
  • 忽视 on-call 与 burnout。最可靠的 SRE 往往最先被耗尽。
  • HRBP 只做协调。不参与业务规划、不看组织健康，就永远在追着补坑。

14.8HRBP 自检清单：十个问题

  1. 我们能否用一句话说清每个 Infra 岗位的「must-have 证据」？
  2. 每个在招岗位，是否有至少 3 个合格候选人，而不是「唯一候选人」？
  3. 面试是否考了真实故障、端到端性能与 on-call，而不是只考概念？
  4. Offer 是否按证据定价，而不是按上一家公司的品牌定价？
  5. 每个新人是否有入职前权限、buddy、30 天 first win？
  6. Infra 的绩效是否成对看（MFU+稳定性、成本+p99），而不是单指标？
  7. On-call 负载是否可见、公平、可补偿？
  8. 关键人是否有备份、文档与轮换？
  9. 季度人力规划是否从业务路线图出发，而不是从 headcount 表出发？
  10. HRBP 是否能在业务会上听懂 GPU、MFU、p99 与 $/1M tokens？
